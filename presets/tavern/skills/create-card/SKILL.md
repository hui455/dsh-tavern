# 新建人物卡

目标：把用户的想法落成能直接开局游玩的人物卡。采用“按需澄清 → 模块初稿 → 局部迭代 → 组装校验”；简单卡直接收束，复杂卡按需展开，不要求每张卡都有世界书、配角、规则和状态栏。

## 访谈

用户开头已给出想法时，先提取已知设定和明确边界，优先确定玩家是谁、与谁互动、开局发生什么。信息足够就给初稿；用户已授权直接做时进入创建。只问缺失且会明显改变结果的部分，一次一个小主题，给 3–4 个差异明确的参考选项，允许自由回答、跳过或“你来定”。不要先把所有字段问完才开始创作；只展示简短设计摘要，不输出完整思维过程。

按需覆盖，已知的跳过：

1. 题材、基调与内容尺度。
2. 角色核心：身份、外貌要点、性格及其内在矛盾、说话方式、与众不同之处。
3. 玩家身份，以及与角色的初始关系。
4. 世界与场景：只有设定较多（势力、地点、规则、术语）时才建世界书。
5. 开场：几个开场、各自的切入时刻；开场要有画面感，并给玩家留出行动空间。
6. 功能选项：先区分是否需要持续追踪状态、是否需要视觉美化；已明确的选项不重复问，未决定的说明含义与代价后由用户选择：
   - MVU 变量：时间、地点、好感、物品等随剧情变化的状态由后台每轮结算，状态栏格式稳定；代价是每轮多一次后台调用。
   - 前端美化：状态栏面板、开场主页等视觉样式。不选 MVU 时，状态栏只能靠模型按约定格式输出、再由正则替换成 HTML，模型偶尔不按格式输出时显示会失效；把这一点讲清楚，由用户决定。

用户回答含糊时用具体场景做二选一；说“随便/你定”时采用贴合已有设定的默认值，并在摘要中标出。轮数由信息缺口决定，不为凑齐清单追问。可调用 `tavern_user_profile_read` 参考长期偏好，但本卡的要求以用户当下回答为准。

## 模块初稿

按用户当前想创作的部分展开，不强制先世界后人物。复杂卡用简短清单标明采用的模块、已确定内容和助手建议；简单卡直接给人物与开场初稿，不额外维护流程表。

- **核心人物**：身份与辨识特征、目标、害怕失去的东西、表面与内在矛盾、对玩家的初始态度、说话与行为习惯。用经历解释性格，用典型情境和对白验证反应；例如“嘴硬但关心人”应体现为先责问晚归、再递上留好的饭，而非反复写性格标签。只补有助扮演的细节，不机械填满长模板。
- **配角**：先写身份、关键关系、剧情作用和一个辨识细节，需要时再展开。关系依据已采用设定，新增关系作为建议说明；不要为每个配角复制主角级长篇档案。
- **世界**：围绕本卡互动需要补地点、势力、术语和运行规则。日常单场景卡不必扩展完整历史或力量体系。人物应符合世界设定。
- **规则**：普通约束用简短自然语言；复杂机制再明确适用对象、触发条件、结果、限制与例外。区分世界内角色知道的规则和只供后台结算的数值，避免角色直接说出不可感知的后台指标。选择 MVU 时补初值、范围和更新条件，不把所有规则都数值化。
- **开场**：未指定数量先写一个完整开场；多开场以不同处境、关系或切入时刻区分，各自独立，不继承其他开场的事件。使用已采用人物与世界，遵守角色知识边界，留下玩家行动空间，不替 `{{user}}` 决定言行和心理。

助手提出的扩展与用户已确定内容分开说明，未采用的候选不进入成品。未来发展是可能方向，不写成既成事实。

## 局部迭代

用户要求修改时定位本次创作的具体人物、规则或开场，以当前采用版本为基础，只改指定部分。只改开场不重写人设；更换职业时检查相关经历、对白和开场的影响。涉及已明确锁定的设定且无法兼容时再询问。

每次简短说明改动及关联影响，不反复输出未变的整张卡。已保存的内容先读取当前资源，用现有编辑工具按范围更新，避免重复创建；保存失败先核对工具回执和资源是否已创建，再继续修复。对话中的候选与摘要不等于持久化版本系统，不承诺未实现的版本切换或恢复能力。

## 美化草图

用户选择前端美化后，给出 2–3 种风格明显不同的草图供挑选，每种一个 ```html 代码块。工作台会把闭合的 html 代码块直接渲染成静态预览。

- 用静态 HTML 和内联 `<style>` 画草图：预览里脚本不运行、外部字体和图片不加载。进度条这类动态效果先画成静态示意，成品里再用脚本实现。
- 使用本卡的示例数据（角色名、地点、状态值），按 360px 窄屏也能阅读设计，长文本能换行。
- 每个草图前用一句话说明风格取向。用户选定或提出修改后，按需再出一版；草图只是示意，正式成品在创建阶段实现。

## 确认设定

信息足够后，给出简短的组装摘要：卡名、玩家身份、采用的核心人物与配角、世界书与规则要点、开场列表及默认开场、功能选项（MVU / 美化及选定草图）。只纳入已采用内容。用户确认或修改后再创建；已明确说“直接做”或已确认同一范围时不重复确认。

## 创建与校验

1. 用 `tavern_update_card` 在空白工作台创建正式人物卡，`fields` 同时提供 `name` 与 `player`。一次写齐：
   - `description`：外貌、身份、背景与关键经历。
   - `personality`：性格、动机、矛盾、说话方式。
   - `scenario`：开局时的处境与关系。
   - `first_mes` 与 `alternate_greetings`：每个开场是一段完整的开局正文，不替 `{{user}}` 决定言行与心理。
   - `mes_example`：2–3 段以 `<START>` 分隔的示例对话，体现语气。
   - `creator_notes` 与 `tags`：简述玩法和题材。
2. 需要世界书时，用 `tavern_update_worldbook` 的 `add` 操作写入条目，path 为新卡的 `cards/...` 路径；entry 用 `comment`、`content`、`primaryKeys`（关键词数组）。每个条目一个主题；配角优先使用准确姓名、别名触发，避免用“老师”等泛称误触发。核心设定保持可用，其他内容按需召回，不在人物字段与常驻条目中重复堆放相同全文。继续修改时更新已有条目，不重复追加。
3. 查看保存结果附带的磁盘校验（直接改文件时调用 `tavern_validate_card`），修复本次引入的问题后重新保存或校验。
4. 选择了 MVU：通过原生 `skill` 加载 `card-to-mvu`，直接在这张卡上加变量、更新规则和状态栏。面板按选定草图实现，可以用样式和脚本还原草图效果；没选美化时做一个简洁的字段列表面板。
5. 选择了美化但不用 MVU：开场主页直接写进开场正文的 ```html 代码块；状态栏在 `system_prompt` 或 `post_history_instructions` 中约定每轮末尾输出固定标签格式，并通过 `rawOperations` 在 `/data/extensions/regex_scripts` 追加正则，把标签替换成选定草图的 HTML（`placement: [2]`、`markdownOnly: true`），另加一条 `promptOnly: true` 的正则从模型历史中移除旧状态块。保存后再次校验。

组装后阅读成品做内容检查：姓名与关系一致，人设、规则和对白不冲突，没有模板占位、未采用候选或创作助手自身指令混入；开场不代替玩家行动，各独立开场的状态初值与正文一致。此项是内容审阅，不宣称格式校验器已验证叙事质量。只修复本次创作引入的问题。

## 交付

报告卡片路径、各开场的切入点、启用的功能和校验结果。告诉用户：在游玩模式选择这张卡，可以预览开场与美化的实际效果。静态校验不等于实际游玩已经验证，只有用户要求时才做真实试玩。

阶段变化时用一句话说明正在做什么。工具报错按回执中的具体字段修正，不盲目重试。
