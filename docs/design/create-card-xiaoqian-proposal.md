## 借鉴点与调整

| 源卡中的依据 | 值得借鉴 | DSH 采用方式 |
|---|---|---|
| 世界观、角色、规则、开场独立标签页和生成模板 | 每次专注一类内容，可单独修改 | 对话中按模块创作，不必先增加多标签界面 |
| 详细人设/简单人设；导出时主角常驻、配角以昵称触发 | 创作详略与上下文成本分层 | 核心人物完整设计，配角先写精简条目；常驻与触发按实际重要性决定 |
| 人设的核心/表面/内在性格、成长经历、小动作、语言习惯 | 人物具有可观察的行为，而非形容词堆积 | 用动机、矛盾、情境反应和示例对白串联设定 |
| 简单/复杂规则；显性/隐性规则区分 | 规则复杂度可选，角色知识与后台数值分开 | 普通叙事约束用自然语言；需状态结算时再引入 MVU |
| 修改指令要求按名字找到原内容、只改指定部分；模板含 version | 局部迭代，保留已认可内容 | 明确修改对象和范围，报告变更；持久化版本选择作为后续能力 |
| 开场必须参考世界/人设，多个开场相互独立，限制全知视角 | 开场是对设定的可玩性检验 | 保留玩家行动空间，检查人物知识边界和各开场初值 |
| 世界观/角色/规则/文风标签数据源，标签切换有输入丢失提醒 | 降低空白创作门槛，保护用户输入 | 给少量贴合当前想法的参考方向，保留自由输入和自定选项 |
| `generateCharacterCard(...selectedItems...)` 按选择组装，测试卡使用时间戳名称 | 先挑选内容，再生成成品 | 成卡前列明纳入模块和开场；测试副本须与正式资源隔离 |
| 发帖可选择概述、背景、开场和作者信息 | 可选的交付包装 | 成卡后按需生成玩法简介；不自动发布或替用户决定授权 |

不直接沿用：强制输出完整思维链、将猜测写成确定事实、每张卡填满固定长模板、默认加入不相关内容、将创作界面脚本带进成品。只向用户展示必要的设计摘要、待决事项与修改说明。源卡的剧情生成器条目处于禁用状态，不作为已启用主流程的依据。

## 优化后的完整流程

### 1. 从已有信息确定创作范围

先提取用户已经给出的题材、人物、玩家身份、关系、开场想法和边界。信息足够就进入初稿；信息不足才按一个小主题提问，提供 3–4 个有区别的参考答案，允许自由回答、跳过和“你来定”。不以固定轮数作为完成条件。

优先弄清三个问题：玩家是谁、主要与谁互动、开局正在发生什么。复杂世界、配角群像和玩法规则随后按需补充。长期偏好仅作参考，本卡要求优先。

### 2. 给出可修改的模块初稿

先提供一张简短的创作清单：本卡需要哪些模块、哪些已确定、哪些是助手建议、哪些仍待决定。它是对话中的工作摘要，不宣称已有新的持久化草稿系统。

- **人物**：身份与辨识特征、当前目标、核心矛盾、对玩家的初始态度、语言和行为样例。
- **世界**：只补本次互动用得上的地点、势力和规则。单场景日常卡可以不另建世界书。
- **配角**：先写身份、与主要人物的关系、剧情作用、一个辨识细节；重要时再展开。
- **玩法规则**：有实际需要才写，明确触发条件、变化结果、限制和例外。
- **开场**：按用户要求生成数量；未指定时先完成一个，增加开场应改变切入处境或关系，而不是只换措辞。

各模块可按用户思路调整顺序。用户只想先写人物时，不强迫先做宏大世界观。

### 3. 用行为检验人物

核心人物至少能回答：想得到什么、害怕失去什么、如何掩饰真实需要、遇到冲突怎样行动。外貌、经历和习惯以能支持扮演为标准，避免无关细节占据上下文。

例如“嘴硬但关心人”可落成：当玩家冒险晚归，她先追问去向，再把留好的饭推过去；对白用“下次不回来就提前说一声”，不直接解释“她其实很担心”。这是行为设计方法，不是要求所有人物采用同一种性格。

人设与示例对白相互核对，避免描述冷静、对白却无缘由地持续失控。成长或关系变化保留可能性，不把未来剧情写成已经发生。

### 4. 局部修改，检查关联影响

用户说“只改开场”时，保持人物背景、关系和规则不变；说“换职业”时，修改职业及确实依赖职业的内容，并简短列出影响。涉及用户已明确锁定的设定发生冲突时再澄清。

每次修改说明“改了什么、影响哪些模块”，不反复输出整张卡。候选方案未采用前，不混进最终内容；助手补全内容在摘要中标为建议，用户授权“你定”后可直接采用。

未来若增加模块版本系统，应按稳定标识保存版本和选中状态，支持恢复；不要只依靠角色名字和聊天中最后一次出现的位置。此项需要单独实现，目前仅为设计要求。

### 5. 按玩法选择状态与美化

把两个决策分开：是否需要持久状态，以及是否需要视觉面板。

- 无动态状态需求：普通卡即可，开场可以单独美化。
- 需要持续追踪地点、物品或关系等：解释 MVU 的收益与后台调用成本，由用户决定。
- 有 MVU 但不需美化：沿用简洁字段面板。
- 需要美化：按现有工作台能力先预览 HTML 草图，再实现选定样式。
- 不用 MVU 但要动态状态栏：说明模型格式输出加正则替换的限制。

数值规则应有初值、范围、更新条件和边界；角色不能无故知道后台数值。各独立开场须使用对应初始状态，不能继承另一个开场已经发生的事件。

此处描述人物卡创作功能的既有能力；若要修改 DSH 工作台本身的布局或交互，另按仓库 UI 流程完成真实截图、Figma 样板确认及 PR。

### 6. 组装并校验

确认摘要列出：玩家身份、核心人物、采用的配角/世界/规则、开场和默认开场、状态与美化方案。用户已授权直接做时，不重复增加确认关卡。

继续使用现有 `tavern_update_card`、`tavern_update_worldbook` 和校验工具。单角色的核心人设写入现有卡片字段；复杂世界与配角分成世界书条目，避免把相同内容同时常驻在多个位置。明确保存到新的资源，不覆盖正在打开的其他人物卡。

检查分三层：

1. **格式**：卡片结构、正则/脚本语法、变量引用和世界书字段，通过现有校验能力处理。
2. **内容**：姓名和关系一致、没有模板占位内容、人物符合世界规则、开场不代替玩家决定言行、没有将未采用候选混入成品。由 Agent 阅读检查，不伪称静态校验器已能完成。
3. **可玩性**：若安排真实试玩，核对人物语气、玩家行动空间、世界书触发及 MVU 更新。未试玩则如实标记，不把保存成功等同于游玩通过。

交付说明卡片路径、开场切入点、启用功能与实际验证结果。发布简介、作者说明和导出按需附加，不自动发布。

## 落地顺序与验收

**优先改进现有 Skill 的创作方法**：模块化初稿、主配角详略、规则分层、局部修改边界、内容一致性检查。可以先使用当前工具和对话界面，无需先增加复杂页面。

**持久化模块版本与选取组装另立功能**：先核查既有工作版/原版与资源快照能力，再确定最小增量。需要稳定标识、并发修改保护、失败恢复和恢复版本行为，不能仅在提示词里宣称支持。

**界面增强在方向明确后设计**：如确需模块进度、版本选取和组装预览，先做一张代表性 Figma 样板；不在本次方案中直接改客户端。

实施时至少验收以下场景：

- 完整设定输入：跳过已回答问题，直接给出初稿或按授权成卡。
- 一句话灵感：只补关键决策，先形成能玩的简单卡。
- 多人物卡：核心人物与配角详略合理，触发词准确且无重复常驻全文。
- 局部修改：只改指定对象，关联影响可说明，已锁定设定不被静默覆盖。
- 多开场：正文与状态独立，不串用剧情或初值。
- 未选 MVU/美化：不擅自增加对应运行能力。
- 保存或校验失败：保留已完成内容，按具体回执修复，不创建重复资源。
